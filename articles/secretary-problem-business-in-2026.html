How-To: Apply the Secretary Problem

Here’s a Python snippet that implements the 37% rule for optimal stopping:

```python

import random

def secretary_problem_simulation(n_offers=100, strategy='37_percent'):

"""

Simulates the secretary problem with n offers.

Returns whether the agent accepted the best offer.

"""

offers = [random.random() for _ in range(n_offers)]

best_offer = max(offers)

if strategy == '37_percent':

threshold = int(0.37 * n_offers)

observed = offers[:threshold]

best_observed = max(observed) if observed else 0

for i, offer in enumerate(offers[threshold:], threshold):

if offer > best_observed:

return offer == best_offer # Success if it's the best

return False

Example: 100 offers with 37% rule

successes = sum(secretary_problem_simulation(n_offers=100) for _ in range(1000))

print(f"Success rate with 37% strategy: {successes/10:.1f}%")

```

This simulation runs 1,000 trials of a secretary problem with 100 offers. The agent observes the first 37 (approximate) and accepts the first subsequent offer that exceeds the best observed so far.

Why This Works

The 37% rule emerges from mathematical analysis of optimal stopping in sequential decision-making. It maximizes the probability of selecting the best option when you can only make one decision, and no recall is allowed. For large sequences (n > 10), this rule achieves a ~37% success rate—better than random.

This method is ideal for:

  • Sales cycles: When to close a deal vs. keep negotiating.
  • Hiring: When to accept an applicant in a sequential interview process.
  • Resource allocation: When to stop observing options and commit.

FAQ

Q: How do I adapt the 37% rule for small datasets?

For small n, the threshold should be adjusted. For instance, with n=5, observe the first 1–2 offers before accepting the first better one. The rule still applies but needs empirical tuning. The 37% is a limit as n approaches infinity.

Q: Can I use this for non-sequential decisions?

The Secretary Problem assumes a sequential process where you must decide immediately after observing each option. If decisions are not sequential, or if you can revisit past options, other methods (like dynamic programming) may be more appropriate.

Q: Is this suitable for real-time decision-making?

Yes, especially in high-volume workflows where decisions must be made quickly without perfect information. The rule is computationally efficient and works well when you have a rough idea of the number of opportunities ahead.
