MLX vs llama.cpp on Apple Silicon: Real Throughput Numbers (2026)

If you run local models on a Mac, the first question is almost always: MLX or llama.cpp? Both serve open-weight models on Apple Silicon, but they are not the same tool. Here are the real trade-offs measured on M-series hardware in 2026.

Throughput: MLX is faster on Apple Silicon

On the same M-series Mac, 4-bit 27–31B models:

  • MLX: ~45–58 tok/s
  • llama.cpp (GGUF): ~38–48 tok/s

MLX wins because it is built for unified-memory-native execution on Apple's chips. The gap widens as model size grows, because MLX keeps more of the model resident in the fast unified memory path.

When llama.cpp is the right call

llama.cpp is not "worse" — it solves a different problem:

  • Portability: GGUF runs on Apple, x86, GPU, CPU, and edge devices. MLX is Apple-only.
  • Ultra-low-RAM quantization: Q2/Q3 GGUF fits models into machines MLX can't.
  • Mature ecosystem: broad tooling, bindings, and server front-ends.

If you need one model file that runs everywhere, llama.cpp is the portable choice.

When MLX is the right call

  • You are on Apple Silicon and want maximum tokens/sec.
  • You want a drop-in OpenAI-compatible server with minimal setup.
  • You are Python-native and want to script the model directly.

A concrete decision rule

| You need… | Pick |

|-----------|------|

| Fastest local inference on a Mac | MLX |

| One model that runs on Mac + Linux + GPU | llama.cpp |

| Q2/Q3 quantization on <16 GB RAM | llama.cpp |

| OpenAI-compatible server, Python-native | MLX |

The part nobody warns you about

Both tools fail the same silent ways on macOS:

1. A shell-injected `PYTHONPATH` shadows the venv — prefix commands with `env -u PYTHONPATH`.

2. Hugging Face weight downloads stall at 0 bytes when the LFS CDN is blocked — force the Xet bridge with `NO_PROXY="*"`.

3. Binding the server to `0.0.0.0` makes it unreachable from the browser — bind `127.0.0.1`.
