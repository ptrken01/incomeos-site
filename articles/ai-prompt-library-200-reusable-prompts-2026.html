200 Copy-Paste Prompts: The Library Structure That Makes Them Reusable

A folder of 200 prompt `.txt` files is useless the day you need one. The value of a prompt library is retrieval and reuse, not volume. Here is the structure that makes a prompt library actually pay off — and the 200 prompts built on it.

Structure before scale

  • Tag by job, not by tool. `sales/objection-reply`, `ops/incident-summary`, `writing/rewrite-tight`. You search by intent.
  • One variable slot per prompt. Mark the input with `{{INPUT}}` so the same prompt serves every case.
  • Keep a one-line "use when" above each. The header is what you scan at 9am.

A reusable pattern

```

use when: drafting a cold reply to a pricing objection

Role: senior AE.

Input: {{INPUT}}

Output: 3 short replies, plain language, no jargon, one question each.

```

When every prompt follows that shape, you can wire them into agents and scripts instead of pasting by hand.

Make them machine-readable

Following the structure in Anthropic's prompt-engineering guide — separate system, context, and task — means the same prompt works in a notebook, an agent loop, or a cron job. Version them in git so a prompt that regresses is one `git revert` away.

From library to pipeline

Once prompts are tagged and slotted, a tiny dispatcher can pick the right one by the `use when` line and feed it `{{INPUT}}`. That is the difference between a prompt collection and a working system.

Test before you trust

Before a prompt enters the library, run it on three real inputs. If the output shape breaks on any of them, fix the prompt, not the input. A library is only as good as its worst-tested member, so the bar is "passes on real cases," not "looks right."
